# SCRUM-127 — Safety Officer identity and access

[Jira story](https://spm-g6t4.atlassian.net/browse/SCRUM-127) · Jerome · Sprint 3 · 3 points.

The new demo identity can open a confirmed-event review queue, inspect an event and
submit the existing SCRUM-128 safety decision. Approval persists `Preparation` and
its actor/time history. Other roles cannot make safety decisions; the Safety Officer
cannot use unrelated event, venue or equipment mutations.

## Setup and demo

1. Apply the existing user/event, login/RBAC and request-clarification setup scripts.
2. Apply `supabase/migrations/20261017074746_scrum_127_safety_officer.sql` in the
   development Supabase SQL Editor. It is safe to repeat. Keep the updated
   `create_events.sql` when rerunning the base event setup.
3. Run Flask on port 5001 with the existing development role-switcher configuration,
   and the frontend with `npm run dev`. Select **Demo Safety Officer** on Home.
4. Open **Review operational safety**. A Coordinator must have confirmed an event
   before it appears. Open it and approve: it moves to **Preparation**. Request
   changes/reject requires a reason and returns it to **Planning**.
5. Switch to each existing role and verify the safety action is absent. Direct API
   attempts receive 403. The backend remains authoritative even if a button is forged.

Do not assume the Safety Officer is user 6. The migration locks identity writes,
advances the identity sequence past existing IDs and inserts one demo identity only
when it is absent. Existing users and role grants are preserved. The existing dropdown
already renders the database-provided list; no role list is duplicated in the browser.

The shared Supabase database was not modified during implementation. All SQL and
real database tests ran in a disposable local PostgreSQL/PostgREST stack. The project
uses its existing demo session for event routes; this story does not change the
project's separate real-login/event-session integration.

## Code-reading guide

| File | Responsibility |
| --- | --- |
| `supabase/migrations/20261017074746_scrum_127_safety_officer.sql` | Extend the role constraint, safely seed the identity and allow the existing safety approval's Preparation status. No new grants, policies or privileged functions. |
| `api/app/events.py` | Safety-only queue; role-based read limited to Confirmed/Preparation; deny generic event listing/status mutation for this role. Existing roles retain their access. |
| `api/app/event_repository.py` | Query only Confirmed events, 25 per page plus one lookahead, with stable date/ID ordering and safe errors. |
| `frontend/src/app/events/safety/page.tsx` | Queue, paging, denied/empty/error states and event links. |
| `frontend/src/app/events/[eventId]/page.tsx` | Wait for the session role and omit the unrelated clarification fetch for Safety Officers. A real 403 on that fetch previously prevented the whole page from loading. |
| Home and app shell | Discoverable Safety Officer action and navigation. |

The queue returns only summary fields. Direct detail/history access remains limited
to the review window even if a Safety Officer has an old event relationship. Generic
status updates are denied to this role, including when it is related to the event.
The existing safety decision endpoint is reused, including its reason and audit rules.
